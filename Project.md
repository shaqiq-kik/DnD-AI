# D&D AI Game Master — Project Report

## Section 1: System Scenarios

This system is a fully interactive AI-powered Dungeon Master for Dungeons & Dragons 5th Edition. It operates as a text-based game loop where the player types natural language actions and receives narrative responses generated by a local Large Language Model (llama3.2 via Ollama). Below are all scenarios the system handles, described in detail.

### 1. Tavern Social Encounters and NPC Dialogue

**What it does:** The AI generates immersive social encounters when the player interacts with NPCs in tavern or social settings. The DM describes the atmosphere, NPC reactions, and dialogue outcomes.

**How the player triggers it:** The player types any social action in exploration mode, such as "I talk to the bartender," "I ask the hooded figure in the corner about rumors," or "I buy a round of drinks for the table."

**Behind the scenes:** The player's input is sent to `get_rag_context()` which queries ChromaDB for relevant lore — in this case, it retrieves the tavern setting description from `data/locations.txt` (e.g., "The Yawning Portal is a famous tavern in Waterdeep..."). This context is appended to the player's action. The `_plan()` method makes a separate LLM call to reason about whether a skill check is needed (e.g., Persuasion DC 12). The enriched prompt — containing game state, plan, RAG context, and the player action — is then sent to the main LLM call with temperature 0.8 for creative, flowing narration.

### 2. Dungeon Exploration and Room Description

**What it does:** The system generates atmospheric descriptions of dungeon rooms, corridors, and environments. It may describe traps, hidden doors, environmental hazards, and enemy positions.

**How the player triggers it:** Actions like "I look around the room," "I search for traps," "I open the heavy stone door," or "I listen at the corridor."

**Behind the scenes:** RAG retrieves dungeon-related lore from `data/locations.txt` (dark dungeon descriptions with traps, oozes, and undead). The planning step reasons about whether a Perception or Investigation check is appropriate. If the AI decides a check is needed, it calls the `roll_for` tool (e.g., `roll_for(skill="Perception", dc=14, player="Theron")`). The tool result is fed back to the LLM, which narrates the outcome — what the player notices or misses.

### 3. Combat Resolution with Attack Rolls and Damage

**What it does:** Handles full D&D combat encounters including attack rolls, damage application, and HP tracking. The system uses tool calling to roll dice and apply damage to the player character.

**How the player triggers it:** The player switches to combat mode by typing `combat`, then describes combat actions: "I attack the goblin with my sword," "I cast Fireball at the group," or "I dodge behind the pillar."

**Behind the scenes:** With mode set to "combat," temperature drops to 0.4 for precise, rules-accurate responses. The AI calls `roll_for(skill="Attack", dc=15, player="Hero")` to determine hit/miss. If enemies attack and hit the player, the AI calls `apply_damage(amount=7)`. This sets `_pending_damage` in the agent, which appends `DAMAGE:7` to the response string. Back in `main.py`, a regex (`re.search(r'DAMAGE:(\d+)', response)`) detects this signal and calls `game_state.update_hp(-7)` to reduce HP. The damage signal is stripped from the displayed text so the player sees clean narration.

### 4. Merchant Bargaining and Persuasion Checks

**What it does:** Resolves merchant interactions, price negotiations, and persuasion attempts using D&D's Charisma-based skill check system.

**How the player triggers it:** "I try to haggle the price down," "I persuade the merchant to give me a discount," "I intimidate the shopkeeper."

**Behind the scenes:** The AI's planning step identifies this as requiring a Persuasion or Intimidation check and determines an appropriate DC based on context (e.g., DC 13 for a friendly merchant, DC 18 for a hostile one). It calls `roll_for(skill="Persuasion", dc=13, player="Hero")`. The d20 roll determines success or failure, and the AI narrates the outcome accordingly. RAG may retrieve marketplace location lore for atmospheric detail.

### 5. Skill Checks (Stealth, Perception, Persuasion, Athletics)

**What it does:** Automatically resolves skill checks using the d20 system with Difficulty Classes. Supports critical success (natural 20), critical failure (natural 1), regular success, and failure.

**How the player triggers it:** Any action that implies uncertainty: "I try to sneak past the guards," "I climb the wall," "I listen at the door," "I try to convince the king."

**Behind the scenes:** The `roll_for` function in `tools.py` rolls a d20 using `random.randint(1, 20)` and compares it against the DC. The result string (e.g., "Hero rolled a 17 for Stealth against DC 14. Success!") is returned to the LLM as a tool result, which then narrates the consequence. The `_plan()` step is critical here — it determines which skill to check and what DC to set before the main response is generated.

### 6. Quest Tracking and Quest Log Management

**What it does:** Maintains a persistent quest log that the player can view at any time. The AI can implicitly assign quests through narrative (the game state supports quest addition programmatically).

**How the player triggers it:** The player types `quests` to view their current quest log. Quests are added to `game_state.quest_log` as the narrative progresses.

**Behind the scenes:** The `GameState` class has an `add_quest(quest)` method and a `quest_log` list. When the player types `quests`, `main.py` iterates over `game_state.quest_log` and prints each entry. The quest log is persisted across sessions via `session.py`, which serializes it to JSON.

### 7. Automated Dice Rolls (d4, d6, d8, d10, d12, d20)

**What it does:** Provides manual dice rolling for any standard D&D die, as well as automated d20 rolls via AI tool calling.

**How the player triggers it:** Manual rolls: `roll 20`, `roll 6`, `roll 12`, etc. Automated rolls happen when the AI decides a skill check is needed and calls `roll_for`.

**Behind the scenes:** The `roll_dice(sides)` function in `tools.py` uses `random.randint(1, sides)` to generate a random result. For manual rolls, `main.py` parses the command, extracts the number of sides, calls `roll_dice()`, and prints the result. For automated rolls, the AI calls `roll_for()` which internally calls `roll_dice(20)` and applies D&D 5e critical hit/miss rules.

### 8. D&D Lore and Rules Retrieval (Monster Stats, Spell Effects)

**What it does:** Retrieves accurate D&D 5e information from a vector database so the AI can reference real monster stats, spell descriptions, class abilities, and game rules rather than hallucinating.

**How the player triggers it:** Any player action that relates to D&D content triggers RAG automatically — mentioning "goblin," "fireball," "stealth," or any game term causes relevant chunks to be retrieved.

**Behind the scenes:** Before every LLM call, `get_rag_context(store, player_input)` queries ChromaDB with the player's raw text. The `nomic-embed-text` model converts the query into a 768-dimensional vector. ChromaDB performs cosine similarity search and returns the top 3 most relevant document chunks. These are appended to the player's action as `[Relevant D&D 5e Rules/Lore]` before being sent to the AI.

### 9. Game State Management (HP, Inventory, Location Tracking)

**What it does:** Tracks the player character's hit points, maximum HP, inventory items, current location, class, and name. Displays this information on a persistent HUD and via the `state` command.

**How the player triggers it:** The `state` command displays the full character sheet. The HUD line (`[HP: 20/20 | Loc: Starting Area | Mode: Exploration]`) is shown before every input prompt.

**Behind the scenes:** The `GameState` class in `game_state.py` encapsulates all character data. Methods include `update_hp(amount)` (clamps between 0 and max_hp), `update_location(new_location)`, `add_item(item)`, `remove_item(item)`, and `add_quest(quest)`. The `display_state()` method formats and prints the full character sheet.

### 10. Session Persistence (Save and Resume Game Sessions)

**What it does:** Automatically saves the game state and entire conversation history when the player quits, and offers to resume the session on next startup.

**How the player triggers it:** Typing `quit` saves the session. On startup, if `session.json` exists, the player is asked "Would you like to resume? (y/n)."

**Behind the scenes:** `save_session()` serializes the `GameState` attributes and the `gm_agent.messages` list (all plain Python dicts) into `session.json` using `json.dump()`. On load, `load_session()` reads the JSON, reconstructs a `GameState` object, and returns the conversation history. The conversation history is assigned to `gm_agent.messages`, allowing the AI to maintain context from the previous session.

### 11. Text-to-Speech Narration

**What it does:** Reads the Dungeon Master's responses aloud using the system's speech synthesis engine, creating an immersive audio experience.

**How the player triggers it:** At startup, the player is asked "Would you like to enable Text-to-Speech narration? (y/n)." If enabled, every DM response is spoken aloud.

**Behind the scenes:** The `tts.py` module uses `pyttsx3` to interface with the operating system's TTS engine (NSSpeechSynthesizer on macOS). The `Narrator` class initializes the engine with a speaking rate of 150 words per minute and maximum volume. The `narrate(text, enabled)` function creates a `Narrator` instance and calls `speak()` only when enabled is `True`. If `pyttsx3` is not installed, the module gracefully degrades — a warning is printed to stderr at import time, and the narrate function becomes a no-op.

## Section 2: Prompt Engineering and Model Parameter Choice

### Base System Prompt

The system prompt is the foundational instruction set that defines how the LLM behaves throughout the entire game session. It is set once during `GMAgent.__init__()` and persists as the first message in the conversation history:

```python
self.base_system_prompt = (
    "You are an expert Dungeon Master for a Dungeons & Dragons game. "
    "You are creative, engaging, and strictly adhere to the rules of D&D 5e. "
    "Keep your responses concise but descriptive. "
    "Address the player directly and resolve their actions based on your judgment. "
    "You have access to exactly TWO tools:\n"
    "1. roll_for(skill, dc, player) — use for ALL dice rolls and skill checks\n"
    "2. apply_damage(amount) — use ONLY when an enemy successfully hits the "
    "player and deals damage. Call this immediately after narrating the hit."
)
```

**Design rationale:** This prompt accomplishes several critical goals:

1. **Role definition** — "You are an expert Dungeon Master" grounds the AI in a specific persona with domain expertise.
2. **Rule adherence** — "strictly adhere to the rules of D&D 5e" prevents the AI from inventing mechanics.
3. **Response format** — "concise but descriptive" prevents overly long walls of text while maintaining narrative quality.
4. **Player focus** — "Address the player directly" ensures second-person narration ("You see a goblin" not "The player sees a goblin").
5. **Tool restriction** — Explicitly listing exactly two tools with precise usage rules prevents the AI from hallucinating non-existent tools or misusing them. The instruction "use ONLY when an enemy successfully hits" prevents spurious damage application.

### Chain-of-Thought Planning Prompt

Before every main response, the `_plan()` method makes a separate LLM call with this prompt:

```python
planning_prompt = (
    f"You are the Dungeon Master planning your next move.\n\n"
    f"{context}\n"
    f"The player just said/did: '{player_message}'\n\n"
    f"Reason step-by-step:\n"
    f"1. What is the player trying to do?\n"
    f"2. Is a skill check needed? If so, what skill and what is the DC?\n"
    f"3. What are the story stakes?\n\n"
    f"Provide your internal reasoning in 3-5 sentences. No narration."
)
```

**Purpose:** This prompt forces the AI to decompose the player's action into logical components before committing to a response. By asking explicit questions (what, skill check?, stakes?), it ensures the AI doesn't skip reasoning steps. The constraint "No narration" keeps the planning output focused on logic rather than prose, preventing it from prematurely narrating before tools have been called.

### Temperature = 0.8 for Exploration

```python
temperature = 0.8 if scenario == "exploration" else 0.4
```

Higher temperature (0.8) during exploration mode increases the randomness of token selection, producing more creative, varied, and surprising narrative descriptions. When a player explores a tavern or forest, they want vivid, unexpected details — not formulaic responses. A temperature of 0.8 allows the AI to take creative risks: choosing unusual adjectives, introducing unexpected NPC behaviors, and crafting atmospheric descriptions that feel fresh across multiple play sessions.

### Temperature = 0.4 for Combat

Lower temperature (0.4) during combat mode constrains the AI to more predictable, rules-accurate outputs. Combat in D&D requires precise mechanical adjudication — attack rolls must be compared to AC, damage must be calculated correctly, and turn order must be respected. A lower temperature reduces hallucination and ensures the AI follows the logical structure established by the planning step: determine if an attack hits, then apply damage, then narrate the result.

### Game State Context Injection

Every prompt includes the current game state, formatted by `_build_context()`:

```python
def _build_context(self, game_state):
    inv_str = ", ".join(game_state.inventory) if game_state.inventory else "Empty"
    quest_str = ", ".join(game_state.quest_log) if game_state.quest_log else "None"

    return (
        f"Here is the player's current status:\n"
        f"- Name: {game_state.name}\n"
        f"- Class: {game_state.char_class}\n"
        f"- HP: {game_state.hp}/{game_state.max_hp}\n"
        f"- Location: {game_state.location}\n"
        f"- Inventory: {inv_str}\n"
        f"- Active Quests: {quest_str}\n"
    )
```

This ensures the AI always knows the player's current HP (important for combat decisions), class (important for determining what abilities are available), location (important for scene consistency), and inventory (important for item usage). Without this, the AI would lose track of the game state between turns.

### RAG Context Injection

Before the player's action reaches the agent, RAG context is appended in `main.py`:

```python
rag_context = get_rag_context(store, player_input)
enriched_action = player_input
if rag_context:
    enriched_action += f"\n\n[Relevant D&D 5e Rules/Lore]:\n{rag_context}"
```

This provides the AI with factually accurate D&D information (monster stats, spell damage, rules mechanics) directly in the prompt, reducing hallucination. The `[Relevant D&D 5e Rules/Lore]` header signals to the AI that this is reference material to use in its response.

### Tool Instruction in System Prompt

The system prompt explicitly restricts tool usage: "You have access to exactly TWO tools." This prevents the LLM from attempting to call non-existent functions or hallucinating tool schemas. The differentiation between `roll_for` (used for ALL checks) and `apply_damage` (used ONLY for enemy hits) gives the AI clear decision criteria for when each tool is appropriate.

## Section 3: Tools Usage

### What is Tool Calling?

Tool calling (also called function calling) is a capability of modern LLMs that allows the model to output structured function invocations instead of (or alongside) natural language text. Rather than generating a response like "I'll roll a d20 for you... let's say you got a 14," the model outputs a structured JSON object specifying a function name and arguments. The host application then executes the actual function and feeds the result back to the model.

Ollama supports tool calling by accepting a `tools` parameter in the `ollama.chat()` API. When tools are provided, the model may choose to call them by populating `response.message.tool_calls` with structured function call objects. The host application checks for tool calls, executes them, appends the results as `role: "tool"` messages, and re-calls the LLM to get the final narrated response.

### The `roll_for` Tool

**Schema:**

```python
{
    "type": "function",
    "function": {
        "name": "roll_for",
        "description": "Roll a d20 for a skill check and determine success or failure",
        "parameters": {
            "type": "object",
            "properties": {
                "skill": {
                    "type": "string",
                    "description": "The name of the skill being checked"
                },
                "dc": {
                    "type": "integer",
                    "description": "The difficulty class (DC) the roll needs to beat"
                },
                "player": {
                    "type": "string",
                    "description": "The name of the player making the check"
                }
            },
            "required": ["skill", "dc", "player"]
        }
    }
}
```

**Purpose:** This tool is the primary dice-rolling mechanism. The AI decides when a skill check is appropriate, selects the relevant skill (Stealth, Perception, Persuasion, Athletics, Attack, etc.), sets an appropriate DC based on the situation, and passes the player's name. The Python implementation rolls a genuine random d20 and applies D&D critical hit/miss rules:

```python
def roll_for(skill: str, dc: int, player: str) -> str:
    roll = roll_dice(20)
    if roll == 20:
        return f"{player} rolled a 20 for {skill} against DC {dc}. Critical success!"
    elif roll == 1:
        return f"{player} rolled a 1 for {skill} against DC {dc}. Critical failure!"
    elif roll >= dc:
        return f"{player} rolled a {roll} for {skill} against DC {dc}. Success!"
    else:
        return f"{player} rolled a {roll} for {skill} against DC {dc}. Failure."
```

### The `apply_damage` Tool

**Schema:**

```python
{
    "type": "function",
    "function": {
        "name": "apply_damage",
        "description": "Apply damage to the player character after an enemy attack",
        "parameters": {
            "type": "object",
            "properties": {
                "amount": {
                    "type": "integer",
                    "description": "Amount of damage dealt"
                }
            },
            "required": ["amount"]
        }
    }
}
```

**Purpose:** When an enemy successfully hits the player, the AI calls this tool to signal damage. The implementation accumulates damage in `self._pending_damage` and returns a `DAMAGE:N` string. After the LLM finishes its response, `main.py` parses this signal with regex and calls `game_state.update_hp(-N)` to actually reduce the player's HP. This two-stage approach (signal then apply) keeps the game state update in `main.py` where it belongs, while allowing the AI agent to trigger it.

### The TOOLS_DEFINITION Structure

The `TOOLS_DEFINITION` list is defined in `tools.py` and imported by `gm_agent.py`:

```python
from tools import TOOLS_DEFINITION, roll_for
```

It is passed to every `ollama.chat()` call that should support tool usage:

```python
response = ollama.chat(
    model=self.model,
    messages=self.messages,
    tools=TOOLS_DEFINITION,
    options={"temperature": temperature}
)
```

The planning call intentionally does NOT receive tools (it's pure reasoning with no side effects).

### Tool Call Handling Loop

The `respond_to_action()` method implements a loop that continues calling the LLM until it produces a final text response with no more tool calls:

```python
while response.message.tool_calls:
    self.messages.append({
        "role": "assistant",
        "content": response.message.content or ""
    })
    for tool_call in response.message.tool_calls:
        tool_result = self.process_tool_call(tool_call)
        self.messages.append({
            "role": "tool",
            "content": tool_result
        })
    response = ollama.chat(
        model=self.model,
        messages=self.messages,
        tools=TOOLS_DEFINITION,
        options={"temperature": temperature}
    )
```

This allows the AI to chain multiple tool calls (e.g., roll for attack, then apply damage) before producing its final narrative response.

### The `calculate_damage()` Function

```python
def calculate_damage(dice_count: int, dice_sides: int, bonus: int = 0) -> dict:
    rolls = [roll_dice(dice_sides) for _ in range(dice_count)]
    total = sum(rolls)
    final = total + bonus
    return {"rolls": rolls, "total": total, "bonus": bonus, "final": final}
```

This utility function supports multi-dice damage rolls (e.g., 2d6+3 for a longsword) and returns detailed breakdown information. It is available for future tool integration or manual damage calculation.

### Connection to the Python Ecosystem

The tools system connects the AI's decisions to real Python execution:
- `random.randint(1, sides)` provides cryptographically fair dice rolls
- The `ollama` library handles all LLM communication via HTTP to the local Ollama server
- Tool arguments are parsed defensively (handling dict, string, and None types) to account for LLM output variability

## Section 4: Planning and Reasoning

### What is Chain-of-Thought Planning?

Chain-of-thought (CoT) planning is a technique where a language model is prompted to explicitly reason through a problem step-by-step before generating its final answer. Research has shown that LLMs produce significantly better outputs when they "think aloud" rather than attempting to jump directly to a conclusion. In this project, CoT planning ensures the Dungeon Master considers the rules, the player's intent, and the narrative stakes before committing to a response.

### The `_plan()` Method

The `_plan()` method makes a completely **separate** `ollama.chat()` call that is independent from the main response generation:

```python
def _plan(self, player_message: str, game_state) -> str:
    context = self._build_context(game_state)
    planning_prompt = (
        f"You are the Dungeon Master planning your next move.\n\n"
        f"{context}\n"
        f"The player just said/did: '{player_message}'\n\n"
        f"Reason step-by-step:\n"
        f"1. What is the player trying to do?\n"
        f"2. Is a skill check needed? If so, what skill and what is the DC?\n"
        f"3. What are the story stakes?\n\n"
        f"Provide your internal reasoning in 3-5 sentences. No narration."
    )
    try:
        response = ollama.chat(
            model=self.model,
            messages=[{"role": "user", "content": planning_prompt}]
        )
        return response.message.content
    except Exception as e:
        print(f"\n[System Warning] Planning step failed: {e}")
        return "No plan generated."
```

Key design decisions:
- **Separate call** — Uses a fresh message list (not the conversation history), preventing the plan from being influenced by or contaminating the ongoing conversation.
- **No tools** — The planning call does not receive `TOOLS_DEFINITION`, ensuring it only reasons and never triggers side effects.
- **Context injection** — Includes the full game state so the plan accounts for HP, location, class, etc.
- **Structured questions** — The three numbered questions guide the AI through a logical decision tree.

### How the Plan Gets Injected

The plan output is embedded into the main response prompt as an internal DM note:

```python
enriched_prompt = (
    f"{context}\n"
    f"[DM Internal Plan]:\n{plan}\n\n"
    f"[Player Action]:\n{player_action}"
)
```

The `[DM Internal Plan]` label tells the AI this is its own prior reasoning, which it should follow when generating the final response. The player never sees the plan — it exists only in the conversation history as part of the user message sent to the LLM.

### Why Planning Improves Response Quality

Without planning, the AI might:
- Forget to call `roll_for` when a skill check is clearly needed
- Set inappropriate DCs (too easy or impossibly hard)
- Lose narrative coherence by not considering the stakes
- Apply damage when no attack actually landed

With planning, the AI has already decided the mechanical resolution before it starts narrating, resulting in responses that correctly sequence: intent → check → outcome → narration.

### Worked Example

**Player input:** "I attack the goblin with my sword"

**What `_plan()` reasons (example output):**
> The player is attempting a melee attack against the goblin. This requires an Attack roll against the goblin's AC of 15. Since the player is a Fighter, they are proficient with swords. The DC should be the goblin's AC (15). The stakes are moderate — the goblin has only 7 HP, so a successful hit could kill it, but a miss means the goblin gets to use Nimble Escape to disengage.

**What the final response looks like:**
> You grip your longsword and lunge at the goblin. [AI calls roll_for(skill="Attack", dc=15, player="Hero")] → "Hero rolled a 17 for Attack against DC 15. Success!" → Your blade catches the creature across its leather jerkin, and it shrieks in pain. The goblin staggers backward, green blood spattering the stone floor.

## Section 5: RAG Implementation

### What is RAG and Why is it Needed?

Retrieval-Augmented Generation (RAG) is a technique that supplements an LLM's knowledge by retrieving relevant documents from an external database and including them in the prompt. This addresses a fundamental limitation of language models: hallucination. Without RAG, if a player asks "How much damage does Fireball do?", the AI might guess incorrectly (e.g., "6d8 fire damage" instead of the correct "8d6 fire damage"). With RAG, the actual spell description is retrieved from the database and included in the prompt, grounding the AI's response in factual information.

### The EmbeddingStore Class

```python
class EmbeddingStore:
    def __init__(self, collection_name="dnd_lore"):
        self.client = chromadb.PersistentClient(path="chroma_db")
        self.embedding_function = OllamaEmbeddingFunction(
            model_name="nomic-embed-text",
            url="http://localhost:11434/api/embeddings"
        )
        self.collection = self.client.get_or_create_collection(
            name=collection_name,
            embedding_function=self.embedding_function
        )
```

This class wraps ChromaDB — an open-source vector database designed for embedding storage and similarity search. The `PersistentClient` stores data on disk in the `chroma_db/` directory, meaning embeddings survive between application restarts without re-computation. The `OllamaEmbeddingFunction` connects ChromaDB to the local Ollama server for generating embeddings.

### The `nomic-embed-text` Model and Embeddings

An embedding is a dense numerical vector (768 dimensions for `nomic-embed-text`) that captures the semantic meaning of a text passage. Similar texts produce similar vectors. For example, the embedding for "I cast a fire spell" would be close to the embedding for "Fireball: A 3rd-level evocation spell..." in vector space. The `nomic-embed-text` model is a lightweight, open-source embedding model optimized for semantic search, running locally through Ollama with no API costs or internet dependency.

### How Lore is Chunked and Loaded

The `load_lore()` function processes the `data/` directory:

```python
def chunk_text(text: str, chunk_size=300) -> list[str]:
    words = text.split()
    chunks = []
    for i in range(0, len(words), chunk_size):
        chunks.append(" ".join(words[i:i + chunk_size]))
    return chunks
```

Each `.txt` file is split into ~300-word chunks. This chunk size balances between too small (losing context) and too large (diluting relevance). Each chunk receives a stable MD5 hash ID based on its content, preventing duplicates when the application restarts:

```python
def generate_id(text: str) -> str:
    return hashlib.md5(text.encode('utf-8')).hexdigest()
```

Before adding documents, the function checks which IDs already exist in the collection and only adds truly new chunks.

### How Cosine Similarity Retrieval Works

When `store.query(query_text, n_results=3)` is called, ChromaDB:
1. Converts the query text into a 768-dimensional vector using `nomic-embed-text`
2. Computes the cosine similarity between the query vector and every stored document vector
3. Returns the top 3 documents with the highest similarity scores

Cosine similarity measures the angle between two vectors — vectors pointing in the same direction (similar meaning) score close to 1.0, while orthogonal vectors (unrelated meaning) score close to 0.0.

### The 5 Data Files

| File | Content |
|------|---------|
| `data/classes.txt` | Fighter, Wizard, Rogue, Cleric, and Ranger class descriptions with mechanics (hit dice, key abilities, signature features) |
| `data/monsters.txt` | Goblin, Skeleton, Orc, Giant Spider, and Young Dragon stat blocks with AC, HP, attacks, and special abilities |
| `data/spells.txt` | Fireball, Magic Missile, Healing Word, Thunderwave, and Sleep spell descriptions with damage, range, and effects |
| `data/rules.txt` | Core d20 mechanics, advantage/disadvantage, initiative, attack rolls, saving throws, and skill check rules |
| `data/locations.txt` | Tavern, dark dungeon, enchanted forest, marketplace, and ancient ruins environment descriptions |

### How `get_rag_context()` is Called

In `main.py`, before every LLM interaction:

```python
rag_context = get_rag_context(store, player_input)
enriched_action = player_input
if rag_context:
    enriched_action += f"\n\n[Relevant D&D 5e Rules/Lore]:\n{rag_context}"
```

The raw player input serves as the search query. The top 3 retrieved chunks are joined with double newlines and appended to the action.

### Concrete Example

**Player types:** "I cast Fireball at the group of goblins"

**RAG retrieves (from `data/spells.txt`):**
> "Fireball is one of the most iconic spells, a 3rd-level evocation that unleashes a devastating explosion... all creatures within that area must make a Dexterity saving throw. On a failed save, a creature takes a staggering 8d6 fire damage..."

**Also retrieves (from `data/monsters.txt`):**
> "The Goblin is a common, small-sized humanoid menace. With an Armor Class of 15... and a meager 7 hit points..."

**Result:** The AI responds with accurate damage ("8d6 fire damage") and knows goblins have 7 HP — likely killing them outright. Without RAG, the AI might hallucinate incorrect damage values or goblin stats.

## Section 6: Additional Tools / Innovation

### Text-to-Speech Feature

The innovation feature for this project is a Text-to-Speech (TTS) narration system that reads the Dungeon Master's responses aloud, transforming the text-based game into an audio-visual experience reminiscent of a real tabletop D&D session with a human DM speaking descriptions aloud.

### The Narrator Class

```python
class Narrator:
    def __init__(self):
        self.engine = None
        if TTS_AVAILABLE:
            try:
                self.engine = pyttsx3.init()
                self.engine.setProperty('rate', 150)
                self.engine.setProperty('volume', 1.0)
            except Exception as e:
                print(f"Warning: Failed to initialize the TTS engine: {e}", file=sys.stderr)
                self.engine = None

    def speak(self, text: str):
        if TTS_AVAILABLE and self.engine:
            self.engine.say(text)
            self.engine.runAndWait()
        else:
            print(f"[Narrator fallback]: {text}")
```

The `Narrator` class encapsulates all TTS functionality:
- **Rate = 150** — Slightly slower than the default (200), creating a more dramatic, deliberate cadence appropriate for a Dungeon Master reading narrative descriptions.
- **Volume = 1.0** — Maximum volume ensures the narration is clearly audible.
- **`speak()`** — Queues text for speech synthesis and blocks until the engine finishes speaking, ensuring narration completes before the next player prompt appears.
- **`set_rate()`** — Allows dynamic adjustment of speaking speed (e.g., faster for combat, slower for dramatic reveals).
- **`stop()`** — Provides the ability to interrupt speech if needed.

### The `narrate()` Function

```python
def narrate(text: str, enabled: bool = True):
    if enabled:
        narrator = Narrator()
        narrator.speak(text)
```

This is the public API used by `main.py`. It accepts an `enabled` flag that is controlled by the player's startup choice. When disabled, the function is a complete no-op — no output, no computation, no side effects.

### Player Control

At game startup, the player is asked:

```python
tts_input = input("Would you like to enable Text-to-Speech narration? (y/n) > ").strip().lower()
tts_enabled = tts_input == 'y'
```

This respects player preference — TTS can be distracting or inappropriate in some environments (libraries, shared spaces). The choice is asked for both new games and loaded sessions.

### Why TTS Enhances the Game Experience

Traditional tabletop D&D involves a human DM speaking narrative descriptions aloud while players listen. This auditory component is a core part of the immersion — hearing a dramatic pause before a dragon attack reveal, or the urgency in a DM's voice during combat. Text-to-Speech bridges this gap for an AI DM, transforming silent text into spoken narration that:

1. Creates atmosphere — Hearing "You hear the scraping of claws on stone..." is more immersive than reading it
2. Allows hands-free play — Players can close their eyes and imagine the scene
3. Increases accessibility — Supports players who prefer auditory information processing
4. Matches the D&D tradition — Preserves the oral storytelling heritage of the game

### Graceful Fallback

The module is designed to never crash the application:

```python
try:
    import pyttsx3
    TTS_AVAILABLE = True
except ImportError:
    TTS_AVAILABLE = False
    print("Warning: 'pyttsx3' is not installed. Text-to-Speech narration is disabled.", file=sys.stderr)
```

If `pyttsx3` is not installed, `TTS_AVAILABLE` is set to `False` at import time. All subsequent calls to `narrate()` with `enabled=True` will use the `Narrator.speak()` fallback path, which prints the text with a `[Narrator fallback]` prefix. If `enabled=False` (user opted out), nothing happens at all.

### Why This Qualifies as Innovation

This feature goes beyond the base requirements of an AI game master by adding a completely new modality of interaction (audio). It requires:
- System-level integration (OS speech synthesis APIs)
- User preference management
- Graceful degradation across different environments
- Careful timing (blocking until speech completes)
- Platform-specific compatibility handling (macOS NSSpeechSynthesizer, Windows SAPI, Linux espeak)

### Single Responsibility Principle

Each file has exactly one job:
- **`main.py`** — The only file that handles user input/output. No other file prints to the terminal (except system warnings).
- **`gm_agent.py`** — The only file that communicates with the LLM. All `ollama.chat()` calls live here.
- **`tools.py`** — The only file that knows about dice mechanics. Pure functions with no side effects.
- **`game_state.py`** — The only file that manages character data. A simple data class with modifier methods.
- **`rag.py`** — The only file that touches ChromaDB. Encapsulates all vector database logic.
- **`session.py`** — The only file that reads/writes JSON files to disk.
- **`tts.py`** — The only file that interfaces with the OS speech engine.

This means any single component can be modified, replaced, or tested independently without affecting the others.

All LLM calls are wrapped in try/except blocks with informative error messages:

